Technologies

The Tech Stack — What We Use and Why

Every library in this project was chosen for a specific reason. Here's what each one does and why we picked it over alternatives.

HTTP Requests
requests

The standard Python library for making HTTP calls — essentially simulating a browser loading a webpage, but without rendering it. We use it to fetch every page we scrape. Simple, fast, and reliable for static sites.

HTML Parsing
BeautifulSoup4

Takes raw HTML (which is full of tags, scripts, and noise) and lets you navigate it like a tree. We use it to strip everything except readable text, and also to find all the <a> and <img> tags. Alternative would be regex — which breaks easily and is much harder to read.

Web Search
ddgs

DuckDuckGo Search — a free Python library that runs web searches without needing an API key. We use it in the discovery phase to find a client's URLs from just their name and phone. No account, no rate limits for moderate usage, works well with Hebrew queries.

AI / LLM
anthropic

The official Python SDK for the Claude API. We use it to send prompts and receive responses. The model we use is claude-sonnet-4-20250514 — a strong balance of intelligence and speed. Alternatives like OpenAI's GPT-4 or Google Gemini could work, but Claude handles Hebrew particularly well.

Environment Variables
python-dotenv

Loads the .env file into the environment so the API key never appears in the code. This is standard practice — you never commit credentials to GitHub. The .env file is in .gitignore.

Hosting (Demo)
Vercel

Deploys static HTML files to the internet instantly with a clean URL. We used it to host the generated website and minisite so the interviewer can click real links. Free tier, deploys in under 10 seconds with the CLI.

What we deliberately did NOT use

TechnologyWhy we skipped it
Playwright / SeleniumBrowser automation is overkill for static HTML sites. It's 60x slower and costs far more in compute. We only need raw text — no JavaScript rendering required.
LangChainAdds abstraction and complexity without adding value for a linear pipeline. Direct API calls give you full control and are easier to debug.
SerpAPI / Google Search APIPaid services. DuckDuckGo's free library does the same job for this use case.
Database (SQLite, Postgres)Overkill for a prototype. JSON files on disk are simpler, portable, and human-readable — perfect for showing an interviewer what the output looks like.
FastAPI / FlaskNo web server needed — this is a command-line pipeline. Adding a web layer would complicate the demo without adding value.
Starting Point

The CRM Trigger — Where Everything Begins

Before a single line of our code runs, something has to kick it off. In a real company that "something" is the CRM system. Understanding this is important because it explains why the pipeline takes the inputs it does.

What is a CRM?

CRM stands for Customer Relationship Management. It's a database where businesses store information about their clients — contact details, what they bought, when they called, notes from meetings. Companies like Zap would use a platform like Salesforce, HubSpot, or Pipedrive.

What is a "trigger"?

A trigger is an automated event. When something happens in the CRM — like a new purchase — the CRM can automatically fire a signal to another system saying "hey, something happened, go do something about it." That signal is called a webhook. It's essentially an HTTP POST request the CRM sends to your system with the relevant data.

Real World

A client buys a package on Zap's website. The payment system notifies the CRM. The CRM fires a webhook — an HTTP POST to our pipeline's server — with a JSON body like:

{
  "event": "new_purchase",
  "client": {
    "name": "יגאל מזגנים",
    "phone": "072-3977065",
    "location": "קריות",
    "package": "website+minisite"
  }
}

Our server receives this, extracts the fields, and starts the pipeline automatically. Zero human involvement.

Our Prototype

We don't have a real CRM or a server listening for webhooks. Instead, we simulate the trigger by typing the same information manually as command-line arguments:

python main.py \
  --name "יגאל מזגנים" \
  --phone "072-3977065" \
  --location "קריות"

The data is identical. Only the delivery mechanism is different — keyboard instead of HTTP.

Where does the CRM appear in the code?

The CRM is involved at two points in the pipeline — once at the start and once at the end. Many people only think of the end part (logging). The start is equally important:

IN
CRM as the trigger (start) The CRM fires the event that starts the whole process. It provides the client's name, phone, and location — the minimum information needed to find and identify the right business online. In our prototype, this is the --name, --phone, --location arguments in main.py.
OUT
CRM as the destination (end) Once the pipeline finishes, everything gets logged back into the CRM under that client's record — the extracted client data, a timestamp of every action taken, and links to all the deliverables. This is what crm.py handles. In real life it would be an API call; in our prototype it writes a JSON file.
One sentence summary: The CRM tells us a new client exists (trigger), we do all the work, then we report everything back to the CRM (log). Our code lives in the middle.
Overview

The Big Picture

The system simulates what happens the moment a new client buys a Zap Group package. In real life, a human account manager would Google the business, read through their website, take notes, and write a welcome message — all manually. This pipeline replaces that entire process with one command.

There are 4 Python files, each with a single clear responsibility. They are wired together by main.py, which runs them in sequence like an assembly line.

CRM trigger → name + phone + location
↓
scraper.py → find URLs → verify → scrape text + images
↓
llm.py → extract data → generate all content
↓
crm.py → log everything with timestamps
↓
output/ client_card.json, welcome_message.md, website/, minisite/

The key insight: the scraper collects raw information, the LLM understands and transforms it, and the CRM logger records everything. main.py just connects them in the right order.

Workflow

The 6-Step Pipeline

1
Discover & Scrape Digital Assets Searches DuckDuckGo for the client's web presence using their name, phone, and city. Each result is verified — the scraper visits the page and confirms the phone number actually appears in the text. Only verified pages are scraped. This prevents picking up a different business with the same name. Then it crawls every internal page of the verified sites and collects real image URLs.
2
Extract Structured Client Card All scraped text (potentially 40,000+ characters) is sent to Claude with a prompt asking it to extract structured JSON — business name, phone, email, services list, brands, service areas, testimonials, and notes for the producer. A second call converts this JSON into a readable Hebrew summary document.
3
Draft 5-Page Website Claude generates 5 complete HTML files — homepage, services, about, areas, and contact. Each page has its own detailed layout spec in the prompt. Real client images (scraped in Step 1) are injected as ready-to-use <img> tags. Frontend design principles (Heebo font, CSS variables, gradient backgrounds, animations) are embedded in the system prompt so the output looks production-quality, not generic.
4
Draft Dapei Zahav Minisite Claude generates a single HTML page that looks like a real d.co.il listing — yellow/gold Dapei Zahav branding, phone/WhatsApp/contact buttons, about section, real gallery photos, service details, business hours, and a contact form. This is what the client's new paid listing will look like.
5
Generate Onboarding Welcome Message Only generated AFTER the website and minisite drafts exist — because the message includes links to both of them. Claude generates a personalized Hebrew message referencing the client's specific services, with placeholder links to the two drafts and questions asking the client to confirm their details. The client receives this before any human at Zap has looked at their file.
6
Log to CRM Creates a structured JSON record with a unique ID (e.g. ZAP-20260408131050), all extracted client data, and a timestamped log of every action taken. In production this would be a POST request to Salesforce, HubSpot, or any CRM API. In the prototype it writes to a local file.

Phase 4 — AI Extraction (llm.py takes over)

The 40,000 character text blob is sent to Claude with a prompt that says: "read all of this and extract the following fields as JSON." Claude reads it all and returns a clean JSON object. This is the client card — the structured representation of everything the scraper found.

Phase 5 — Content Generation

Three more sets of API calls generate all the deliverables. The welcome message is one call. The website is five separate calls — one per page — because generating all 5 pages in one call would hit token limits and produce lower quality. The minisite is one call with a detailed layout spec.

call 5: contact.html — phone, form, WhatsApp

generate_draft_minisite(client_card_json, images)

→ saved as welcome_message.md

Phase 6 — CRM Logging (crm.py takes over)

The final step. crm.py takes the client card JSON and the welcome message, builds a Python dictionary representing a CRM record, and writes it to a JSON file. In a real system this dictionary would be serialized and sent as the body of an HTTP POST request to a CRM API.

crm.py — log_to_crm(client_card_json, welcome_msg, OUTPUT_DIR)

builds crm_entry dict with: client_data, actions_taken[], deliverables{}
json.dump(crm_entry, file) → output/crm_log.json
# in production: requests.post(CRM_API_URL, json=crm_entry, headers=auth)
Total API calls to Claude in one full run: 8 calls — 1 for extraction, 1 for Hebrew summary, 1 for welcome message, 5 for website pages, 1 for minisite. Each call is independent; none depends on the response of another (except the extraction, which all generation calls use as input).

scraper.py
Finds the client on the internet and reads their websites

What problem does it solve?

The system only knows a business name, phone number, and city — it has no URL. This file's job is to go find where the business exists online, make sure each result actually belongs to the right business, and then read all the content from those pages.

Function 1 — discover_assets(name, phone, location)

This is the "find the client" function. It runs 4 different DuckDuckGo searches — a phone-first query (most reliable for Israeli businesses), a name + location query, and directory-specific queries. It collects all unique URLs from the results, then visits each one to check whether the phone number appears on the page. Only URLs where the phone matches are kept.

Why phone-first queries? When tested, searching "072-3977065 מזגנים" immediately returned imazganim.co.il and prosites.co.il — the two most relevant results. Searching by name alone returned many unrelated businesses. The phone number is the unique identifier that anchors everything to the right person. 
# Example: cross-verification logic
def _phone_variants(phone):
    digits_only = re.sub(r"\D", "", phone)       # 0723977065
    with_dash = re.sub(r"(\d{3})(\d+)", r"\1-\2", digits_only)  # 072-3977065
    return {phone, digits_only, with_dash, digits_only[1:]}

# Then for each candidate URL:
if any(v in text for v in variants):
    verified.append(url)   # ✓ right business
else:
    pass                   # ✗ skip it

Function 2 — scrape_url(url)

The core scraping function. It makes a simple HTTP GET request using the requests library (like a browser loading a page, but without rendering JavaScript). Then BeautifulSoup parses the HTML, strips out all the noise (script tags, style tags, navigation menus), and extracts just the human-readable text.

Why not use a real browser (Playwright)? During development, browser-based scraping cost around 61 tool calls for one site — each page load, screenshot, and read is a separate operation. A simple requests.get() does the same in a single call. For static websites (which most Israeli small-business sites are), there's no need for a browser.

Function 3 — discover_internal_pages(base_url)

Once we have the homepage, this function reads all the links on it and finds every internal page — things like /services, /contact, /about. It only keeps links that stay on the same domain, so it doesn't accidentally follow external links. This is how we scraped 14 pages from Yigal's site automatically without knowing the URLs in advance.

Function 4 — collect_images(base_url)

Crawls the client's pages looking for <img> tags. It filters out: data URIs (base64 embedded images), images hosted on external CDNs, and files that aren't proper photos (.jpg, .png, .webp). Returns up to 8 real photo URLs from the client's own domain. These are passed to the LLM so it can include real images in the gallery instead of grey placeholders.

llm.py
All Claude API calls — extraction and content generation

What problem does it solve?

Raw scraped text is unstructured. It might be 40,000 characters from 14 different web pages, in no particular order. This file sends that text to Claude with carefully written prompts that tell it exactly what to extract or generate. Every AI call in the project goes through here.

The call_claude() helper

All 5 AI functions use this one helper under the hood. It sets up the API client, sends the system prompt + user prompt to Claude, and returns the text response. Having one central function means you can change the model, add logging, or adjust settings in one place.

def call_claude(system_prompt, user_prompt, max_tokens=2048):
    client = anthropic.Anthropic()
    message = client.messages.create(
        model="claude-sonnet-4-20250514",
        max_tokens=max_tokens,
        system=system_prompt,
        messages=[{"role": "user", "content": user_prompt}]
    )
    return message.content[0].text

The DESIGN_SYSTEM_PROMPT constant

This is the most important design decision in llm.py. The first version of the generated websites looked generic — flat white backgrounds, Arial font, basic layouts. The solution was to extract the principles from Claude Code's /frontend-design skill and embed them directly into the system prompt sent to the API.

The key insight: The /frontend-design skill is a Claude Code feature — it can't be called from outside Claude Code. But its design principles are just text. So we read them and copy-pasted the rules into our own system prompt. The model then applies those rules to every website and minisite it generates.

The embedded rules include: use Google Fonts (specifically Heebo for Hebrew text), define colors as CSS custom properties in :root, use gradient or textured backgrounds (never flat white), add CSS transitions and staggered animations, use generous negative space and asymmetric layouts.

How generate_draft_website() works

Rather than generating all 5 pages in one massive prompt, the function loops through a dictionary of page specs — each page has its own description of what it should contain and how it should look. Claude is called once per page. The results are returned as a dictionary of filename → html_string.

max_tokens is set to 8192 for these calls (double the default) because rich HTML with inline CSS can easily be 300–500 lines long — a lower limit would cut the file off mid-tag.

How image injection works

The _format_images() helper converts the list of scraped image URLs into a block of ready-to-paste HTML that goes directly into the prompt. The model is told: "use these URLs in <img> tags, do not use placeholders." This is how the minisite gallery shows real photos from the client's own website.

# What the model sees in the prompt:
REAL IMAGES FROM CLIENT'S SITE (use these in <img> tags):
  1. <img src="https://www.imazganim.co.il/.../installation.jpg" alt="התקנת מזגנים">
  2. <img src="https://www.imazganim.co.il/.../repair.jpg" alt="תיקון מזגנים">

main.py
The orchestrator — runs everything in order

What problem does it solve?

The other three files each do one thing well. main.py is the glue that connects them, runs them in the right sequence, handles command-line arguments, creates output directories, and saves every generated file to disk.

Two run modes

The file uses Python's argparse library to accept different input styles:

# Discovery mode — simulates a real CRM trigger
python main.py --name "יגאל מזגנים" --phone "072-3977065" --location "קריות"

# Direct URL mode — you already know the client's website
python main.py --url https://www.imazganim.co.il/

# No args — uses the demo client (fastest for testing)
python main.py
Why two modes? Discovery mode is what a real production system would use — the CRM fires a trigger with just the client's name and phone. Direct URL mode is useful for testing and for cases where the client provides their URL during the purchase checkout process.

The run_pipeline(scraped_results, base_url) function

Once scraping is done, both modes converge into this single function. It doesn't care how the text was collected — it just processes it. This separation is good design: scraping and generation are independent concerns. You could swap out the scraper without touching the generation logic.

Step 4b — Auto-deploy to Vercel

After the website and minisite HTML files are saved, the pipeline automatically deploys them to Vercel using the Vercel CLI. This is what makes the welcome message contain real clickable links instead of placeholder brackets.

The deploy_to_vercel() function runs vercel deploy --prod --yes as a subprocess, captures the output, and extracts the live URL with a regex. That URL is then passed directly into generate_welcome_message() so Claude writes it into the message.

If Vercel is not installed or the deploy fails, the pipeline falls back to placeholder links — it never crashes because of a deployment failure.

Prerequisite: The Vercel CLI must be installed and authenticated before running the pipeline: 
npm install -g vercel
vercel login

Output structure

Every file generated by the pipeline is saved under output/. The function calls os.makedirs() at the start to make sure the folders exist. File saving is handled by a simple save_file() helper that takes a relative path and content string.

crm.py
Simulates logging the completed onboarding back to the CRM system

The single function: log_to_crm()

This is the simplest file in the project. It has one job: take everything the pipeline produced and package it into a structured record. In production that record gets sent to a CRM platform. In our prototype it gets saved as a JSON file you can open and read.

Real vs. Prototype — side by side

Real World

The last line of log_to_crm() would be an HTTP POST to a CRM API:

requests.post(
  "https://api.hubspot.com/crm/v3/objects/contacts",
  json=crm_entry,
  headers={"Authorization": "Bearer " + API_KEY}
)

The CRM would store the record in a database, attach it to the client's profile, and make it searchable for the account manager.

Our Prototype

The last line writes to a local file instead:

json.dump(crm_entry, file,
  ensure_ascii=False,
  indent=2
)

The JSON file is saved as output/crm_log.json. The structure of the data is identical to what a real CRM would receive.

The function builds a Python dictionary with 6 fields. Here's what each one is and why it's there:

The action log — what it looks like

The actions_taken field is a list of records, one per pipeline step. Each record has the action name, timestamp, and a human-readable description. This is what an account manager or a support team would see if they pulled up this client's record in the CRM.

# The 5 actions logged, in order:
{ "action": "digital_assets_scanned",   "timestamp": "2026-04-08T13:10:50" }
{ "action": "client_card_generated",    "timestamp": "2026-04-08T13:10:50" }
{ "action": "welcome_message_sent",     "timestamp": "2026-04-08T13:10:50", "channel": "email" }
{ "action": "draft_website_generated",  "timestamp": "2026-04-08T13:10:50" }
{ "action": "draft_minisite_generated", "timestamp": "2026-04-08T13:10:50" }
Important to understand: The timestamps in the prototype all look the same because we build the entire CRM entry at once at the end of the pipeline. In a real system, each action would be logged the moment it happened — so the timestamps would be minutes apart and reflect the real duration of each step.

What is NOT in this file

Notice that crm.py does not do any scraping, AI calls, or HTML generation. It only takes data that was already produced by the other files and formats it. This is intentional — each file has one clear responsibility and does not cross into another file's territory. If tomorrow Zap switches from HubSpot to Salesforce, only this file needs to change.

For the Interview

Key Concepts to Know Cold

Why did you use requests + BeautifulSoup instead of a browser?

Browser automation (Playwright, Selenium) renders JavaScript and is very powerful — but it's slow and expensive in API credits. During our research phase, one agent using Playwright made 61 tool calls just to read one site. requests.get() fetches the same page in a single network call. Since Yigal's site (and most Israeli small-business sites) is static HTML with no JS rendering required, a simple HTTP request is faster, cheaper, and equally effective.

How does the system make sure it found the right business?

Phone number cross-verification. When you search "Yigal AC technician Krayot," you get results for many different people named Yigal. The unique identifier is the phone number from the CRM. Every candidate URL is scraped, and the phone (in several formats — with/without dashes, with/without country code) is searched in the text. Only pages where the phone appears are kept.

What is a system prompt vs. a user prompt?

The Claude API accepts two messages: a system prompt (persistent instructions that set the model's role and rules — in our case, the design principles) and a user prompt (the actual task for this specific call — the page spec and client data). The system prompt is like giving someone their job description; the user prompt is giving them today's task.

What's simulated vs. what's real?

The scraping, AI extraction, and HTML generation are all real — they run against actual live websites. What's simulated is: (1) the CRM write (a JSON file instead of an API call) and (2) the message sending (a markdown file instead of an email/WhatsApp API call). In production, both would be API calls to whatever platforms Zap uses.

Why generate 5 pages separately instead of one big prompt?

Context limits and quality. A single prompt asking for an entire 5-page website would either hit the output token limit (cutting off mid-file) or produce lower-quality results across all pages because the model has to split its attention. Generating one page at a time lets each page get a focused, detailed spec — and each page can be as long as it needs to be.
