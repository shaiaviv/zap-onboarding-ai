argparse, parser, group — from scratch

When you run the program you type something like this in the terminal:

python main.py --name "יגאל מזגנים" --phone "072-3977065" --location "קריות"

argparse is the tool that reads what you typed and makes sense of it. Without it, Python has no idea what --name or --phone mean.


The three lines that set it up:

  • parser = argparse.ArgumentParser() — creates the reader. Like opening a blank form.
  • parser.add_argument("--phone") — adds a field to the form. Now the program knows --phone is a valid thing to pass.
  • args = parser.parse_args() — reads what you actually typed and fills in the form. After this line: args.phone = "072-3977065", args.name = "יגאל מזגנים", etc.

Now — what is group?

The program has two completely different modes:

  • Discovery mode: you give it a name → it searches DuckDuckGo → finds the URLs itself
  • Direct mode: you give it a URL → skips the search → goes straight to scraping

These two modes make no sense together. If you pass both --url and --name, what should the program do? That's why they're put in a group — argparse will automatically throw an error if you try to pass both. It's just a safety rule. --phone and --location are NOT in the group because they don't conflict with anything.

parser  (the whole form)
├── group  (pick ONE only — these conflict)
│   ├── --url
│   └── --name
├── --phone     (no restriction — always optional)
└── --location  (no restriction — always optional)

How does it actually decide which mode to run?

The group doesn't decide — it just stops you from passing both at once. The real decision is one plain if after parsing:

if args.name:        # did the user type --name?
    discover_assets(...)   # yes → search for URLs
else:
    scrape_client(...)     # no → use --url or demo
  • Typed --name "יגאל" → args.name = "יגאל" → truthy → discovery mode
  • Typed --url https://... → args.name = None → falsy → direct mode
  • Typed nothing → args.name = None, args.url = None → direct mode → falls back to DEMO_URL

Why do we skip Facebook, Instagram, X, etc.?

Reason 1 — you can't scrape them. These platforms require you to be logged in to see any real content. If you try to scrape them with requests.get() (which has no login), you get a login wall — not the business's actual posts. You'd be scraping a page that says "sign in to continue", which is useless.


Reason 2 — even if you could, the content is noise. The scraper is looking for clean business information: phone numbers, service descriptions, addresses. Social media pages are packed with garbage: reaction counts, "share", "follow", "sponsored", timestamps, recommended posts from other accounts. Claude would have to wade through massive amounts of junk to find one phone number.


Why is it a set and not a list?

SKIP_DOMAINS = {"google.com", "facebook.com", ...}  # set — curly braces, no key:value

The check later is if skip in domain — a membership test. A set answers that instantly no matter how many items it contains. A list would check one by one. For 11 items it makes no real difference, but a set is the semantically correct choice for "is this thing a member of this collection."

raise_for_status() — why "success" isn't always success

When you make an HTTP request, the server always responds — even for pages that don't exist. A 404 (Not Found) is still a response. Without raise_for_status(), the code would happily continue with the 404 error page's HTML content as if it were real data.

resp = requests.get(url)
resp.raise_for_status()   # throws an exception if status is 4xx or 5xx
# 200 OK      → continues normally
# 404 Not Found → raises exception → caught by except → returns "[ERROR...]"
# 500 Server Error → same

apparent_encoding — why Hebrew breaks without it

Every text file is stored as bytes. Encoding is the rulebook that maps those bytes to characters. Hebrew websites often use Windows-1255 or ISO-8859-8 instead of UTF-8. If you read the bytes with the wrong encoding, you get garbage like ×™×'×¢×œ instead of יגאל.

resp.apparent_encoding uses the chardet library to analyze the actual byte patterns and guess the correct encoding — the same way a human would look at text and tell if it's garbled. It's not perfect, but it handles the vast majority of Israeli websites correctly.

try/except + returning "[ERROR...]" instead of crashing

A normal function would raise an exception when something goes wrong and let the caller deal with it. scrape_url() makes a different choice: it catches every possible exception and returns a string that starts with [ERROR.

Why? Because the scraper calls this function in loops — scraping 10, 20, 30 URLs in one run. If one URL fails, we don't want the whole pipeline to crash. We want it to note the failure and move on. The callers check if text.startswith("[ERROR") and skip bad results. This is a deliberate design pattern called "error as value" — the error is just another return value, not an exceptional event.

any() with a generator expression

This pattern appears multiple times in the project:

if not any(ext.endswith(e) for e in [".jpg", ".jpeg", ".png", ".webp"]):
    continue

any() returns True if at least one item in an iterable is truthy. The part inside is a generator expression — like a list comprehension but it doesn't build the full list, it evaluates one item at a time and stops as soon as one is True (short-circuit).

The long version of the same thing:

found = False
for e in [".jpg", ".jpeg", ".png", ".webp"]:
    if ext.endswith(e):
        found = True
        break
if not found:
    continue

any(condition for x in iterable) replaces all of that with one line. You'll see it used alongside all() — which requires every item to be truthy instead of just one.

urlparse() — the right way to pull apart a URL

A URL has distinct parts. urlparse() splits them cleanly:

url = "https://www.imazganim.co.il/services?lang=he#top"

urlparse(url).scheme   → "https"
urlparse(url).netloc   → "www.imazganim.co.il"   ← the domain
urlparse(url).path     → "/services"
urlparse(url).query    → "lang=he"
urlparse(url).fragment → "top"

The project uses .netloc constantly — to compare domains, to filter external links, to extract a domain name. The alternative (splitting on "://" and "/" manually) is fragile and breaks on edge cases. urlparse() handles every valid URL format correctly.

set vs list — and when to use which

_phone_variants() returns a set, not a list:

return {phone, digits_only, with_dash, digits_only[1:]}  # set — curly braces

Two reasons:

  • No duplicates. If the user passes a phone number that's already in one of the normalized forms (e.g. they pass "0723977065" with no dash), the set automatically collapses that to 3 items instead of having the same number twice.
  • Membership check is the only use. The variants are only ever used in if any(v in text for v in variants). You never need to access them by index, sort them, or loop in a specific order. A set is the right tool for "is this thing in this collection?"

Rule of thumb: use a list when order or duplicates matter. Use a set when you only care about membership and uniqueness.

sum() with a generator — aggregating across a dict

total_chars = sum(len(v) for v in results.values())

Break it down piece by piece:

  • results.values() — gives you all the scraped text strings (not the URL keys, just the values)
  • len(v) — gets the character count of each string
  • for v in ... — the generator expression iterates through each value
  • sum(...) — adds all those character counts together

The long version: total = 0; for v in results.values(): total += len(v). The generator inside sum() collapses that into one line. This is the same pattern as any() — Python built-ins like sum(), max(), min(), any(), all() all accept generators directly.

How the markdown stripping works — split + rsplit

Claude sometimes wraps its response in markdown code fences even when told not to:
```json
{"business_name": ...}
```

The fix is a two-step strip:

  • result.split("\n", 1) — splits on the FIRST newline only. The second argument 1 means "max 1 split". Result: ["```json", '{"business_name"...}```']
  • [1] — takes the second part (everything after the first line, i.e. the actual JSON + closing fence)
  • .rsplit("```", 1) — splits from the RIGHT, at the last occurrence of ```. Result: ['{"business_name"...}', '']
  • [0] — takes the first part (the clean JSON, no trailing fence)

Why rsplit instead of split for the second step? Because the JSON itself could contain backticks — splitting from the right guarantees we only cut the final closing fence.

The "or []" default pattern — Python's falsy shortcut

images or [] is Python's idiomatic way to handle optional parameters that default to None.

Why not just use def f(images=[])? — Mutable default arguments in Python are a famous gotcha: the [] is created once when the function is defined, not each time it's called. If you append to it, the next call sees the modified list. Using None + or [] is the safe pattern.

  • If images is None → None or [] → [] (because None is falsy)
  • If images is an empty list → [] or [] → [] (empty list is also falsy)
  • If images is a real list → [img1, img2] or [] → [img1, img2] (truthy, short-circuits)

You'll see this pattern everywhere in Python. Equivalent to: images if images is not None else []

Three crm.py patterns worth knowing

1. isinstance(client_card, str) — defensive type check

log_to_crm() can receive client_card as either a JSON string (from the file we saved) or as a Python dict (if called directly with already-parsed data). isinstance(x, str) returns True if x is a string. The inline ternary A if condition else B is Python's single-line if/else — same as:

2. strftime('%Y%m%d%H%M%S') vs isoformat()

  • strftime('%Y%m%d%H%M%S') → "20260425132346" — custom format, no separators, safe for IDs
  • %Y=4-digit year, %m=month, %d=day, %H=hour (24h), %M=minute, %S=second
  • isoformat() → "2026-04-25T13:23:46.123456" — ISO 8601 standard, what databases and APIs expect
  • We use both: strftime for the CRM ID (must be a clean string), isoformat for the timestamp field (must be parseable by any system)

3. json.dump parameters — ensure_ascii and indent

  • ensure_ascii=False — by default, json.dump converts non-ASCII characters to \uXXXX escape sequences. Setting False keeps Hebrew as-is: "יגאל מזגנים" not "\u05d9\u05d2\u05d0\u05dc..."
  • indent=2 — pretty-prints with 2-space indentation. Without it, the JSON is one long line. With it, it's human-readable in any text editor
  • The file is opened with encoding="utf-8" to match — otherwise the Hebrew would fail to write
