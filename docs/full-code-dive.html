main() main.py

3

Back in main.py. Takes the scraped dict from step 2 and runs all remaining steps in order. This is the orchestrator — it doesn't do the work itself, it calls functions from scraper.py, llm.py, and crm.py.

4

Called FROM run_pipeline() in main.py, lives IN scraper.py. Crawls the client's site looking for .jpg/.png/.webp images hosted on their own domain. Returns a list of [{"url": "...", "alt": "..."}]. These get injected into the LLM prompts later.

5

Called FROM run_pipeline(), lives IN llm.py. Sends all scraped text to Claude. Gets back a JSON string with business name, phone, services, etc. Saved to output/client_card.json. The same JSON is reused by every step after this.

internally calls:
call_claude(system, prompt, max_tokens=4096) → the actual API call
6

Takes the JSON from step 5, sends it to Claude again with a different system prompt. Claude reformats it as a readable Hebrew document for the Zap producer. Saved to output/client_card.md.

7
generate_draft_website(client_card_json, images) llm.py

Loops through 5 page specs. Makes 5 separate Claude API calls — one per page. Each call gets DESIGN_SYSTEM_PROMPT as the system prompt and the page spec + client JSON as the user prompt. Returns a dict of 5 HTML files. Saved to output/website/.

internally calls:
_format_images(images) → converts image list to prompt text
call_claude(...) × 5 → one API call per page
8

One Claude API call. Generates a single HTML file styled like a Dapei Zahav directory listing. Different system prompt than the website — targets yellow/gold aesthetic. Saved to output/minisite/index.html.

9

One Claude API call. Writes the Hebrew welcome message for the client. Deliberately runs AFTER steps 7 and 8 — because the message contains links to the website and minisite drafts that must exist first. Saved to output/welcome_message.md.

10

Called FROM run_pipeline(), lives IN crm.py. Builds a structured dict with crm_id, timestamps, actions taken, and a preview of the welcome message. Saves to output/crm_log.json. In production: requests.post() to Salesforce.

All web scraping logic — HTTP requests, HTML parsing, DuckDuckGo search, phone verification, image collection.

💡 How we actually get client information

Before reading the code, understand the 3-step chain. Every piece of client data we extract starts here:

1. requests.get(url)
Fetches the raw HTML of a webpage. Exactly what a browser does — but in Python code.
2. BeautifulSoup
Parses the raw HTML, strips all tags, JavaScript and CSS, returns clean readable text.
3. Claude API
Receives the clean text and extracts structured JSON — business name, phone, services, etc.
What requests.get() returns vs what Claude needs
RAW HTML (what requests returns)
<html>
<script>lots of JS...</script>
<style>.header{color:red}</style>
<h1>יגאל מזגנים</h1>
<p>התקנה ותיקון מזגנים</p>
<nav><a href="/about">אודות</a></nav>
</html>
CLEAN TEXT (after BeautifulSoup)
יגאל מזגנים
התקנה ותיקון מזגנים
טלפון: 072-3977065
אודות
The User-Agent header — why we fake being Chrome

Every HTTP request carries a User-Agent header — a label identifying who is making the request. Servers read this and decide whether to respond.

DEFAULT — gets blocked
python-requests/2.28.0

Server sees "bot" → returns 403 or captcha

OUR HEADER — passes through
Mozilla/5.0 (Macintosh...)

Server sees "Chrome on Mac" → serves real page

This is legal and extremely common — you're reading publicly visible pages, just announcing yourself differently. For sites with advanced bot detection (JS checks, cookie tracking) you'd need Playwright. Israeli business sites don't need that.

32def scrape_url(url, encoding=None):
33    try:
34        resp = requests.get(
35            url,
36            headers=HEADERS,
37            timeout=TIMEOUT
38        )
39        resp.raise_for_status()
40        if encoding:
41            resp.encoding = encoding
42        else:
43            resp.encoding = resp.apparent_encoding
44        soup = BeautifulSoup(
45            resp.text, "html.parser"
46        )
47        for tag in soup(["script","style","noscript"]):
48            tag.decompose()
49        text = soup.get_text(
50            separator="\n", strip=True
51        )
52        lines = [
53            line for line in text.splitlines()
54            if line.strip()
55        ]
56        return "\n".join(lines)
57    except Exception as e:
58        return f"[ERROR scraping {url}: {e}]"
Line by line
try: ... except Exception as e:
Catch everything that can go wrong. Network timeout, DNS failure, 404, 503 — any of these throw exceptions. Instead of crashing the whole pipeline, we catch and return an error string starting with "[ERROR". Callers check for this prefix.
requests.get(url, headers=HEADERS, timeout=TIMEOUT)
HTTP GET request. HEADERS contains a fake browser User-Agent — without it, many sites block Python scripts. TIMEOUT=10 means: if the server doesn't respond in 10 seconds, give up and raise a Timeout exception (caught above).
resp.raise_for_status()
Turns HTTP errors into Python exceptions. By default, requests.get() "succeeds" even on 404 Not Found or 500 Server Error — it just gives you the error page. raise_for_status() throws an exception for any 4xx/5xx code, so the except block catches it.
resp.encoding = resp.apparent_encoding
Fixes Hebrew text corruption. Old Israeli sites often use Windows-1255 encoding. requests guesses wrong. apparent_encoding uses chardet to analyse the actual bytes and pick the right encoding — crucial for getting Hebrew characters instead of garbled text.
soup(["script", "style", "noscript"]) tag.decompose()
Removes noise before extracting text. soup([...]) finds all tags of those types. decompose() removes each one from the tree entirely. Without this, get_text() would include hundreds of lines of JavaScript code and CSS rules mixed into the business description.
lines = [line for line in text.splitlines() if line.strip()]
List comprehension — filters empty lines. splitlines() cuts the text at every newline. The if line.strip() condition keeps only lines that have at least one non-whitespace character. This removes blank lines and lines with only spaces — reducing token waste when sending to Claude.

Returns all the different ways a phone number might be written on a website. Used to cross-verify that a found URL actually belongs to this client.

in"072-3977065"
out{"072-3977065", "0723977065", "723977065", "072-3977065"}
full code
122def _phone_variants(phone):
123    digits_only = re.sub(r"\D", "", phone)
124    with_dash = re.sub(
125        r"(\d{3})(\d+)", r"\1-\2", digits_only
126    )
127    return {
128        phone,
129        digits_only,
130        with_dash,
131        digits_only[1:]
132    }
Line by line
re.sub(r"\D", "", phone)
Regex: remove everything that is not a digit. \D means "non-digit character." re.sub replaces all matches with "" (empty string). "072-3977065" → "0723977065". This gives the raw digits to build other formats from.
re.sub(r"(\d{3})(\d+)", r"\1-\2", digits_only)
Regex with capture groups — adds a dash. (\d{3}) captures the first 3 digits into group 1. (\d+) captures the rest into group 2. r"\1-\2" replaces the whole match with "group1-group2". "0723977065" → "072-3977065".
digits_only[1:]
String slice — removes the leading 0. [1:] means "from index 1 to the end." "0723977065" → "723977065". Some directory sites store numbers without the leading zero.
return { phone, digits_only, with_dash, digits_only[1:] }
Returns a set, not a list. Curly braces {} with items separated by commas = a set. Sets have no duplicates and fast membership testing. When we check if any(v in text for v in variants), Python uses the set efficiently.
💡 DuckDuckGo vs requests — two different tools, one job

They look similar but solve completely different problems. Understanding this distinction is key to explaining the discovery mode.

DuckDuckGo (ddgs)
"I don't know the URL — find it for me."
You give it a search query. It returns a list of URLs that match. Like typing into Google — you get results, not page content.
requests
"I know the URL — fetch its content."
You give it a URL. It fetches the actual page and returns the HTML. You must already know the address.
How they work together in discover_assets()
1
DuckDuckGo: ddgs.text("072-3977065 מזגנים")
Returns: ["https://imazganim.co.il", "https://prosites.co.il/...", "https://bakrayot.co.il/...", ...]
We don't know which of these are actually Yigal's. Some might be wrong.
2
requests.get() each candidate URL
Fetches the actual page content of each URL from step 1.
3
Check: does "072-3977065" appear in the page text?
✓ imazganim.co.il — phone found → verified
✗ bakrayot.co.il — different phone → rejected
Why not just use DuckDuckGo results directly? Because DuckDuckGo can return the wrong Yigal. There could be another AC technician named יגאל somewhere else in Israel. The phone verification step is what separates "probably his" from "definitely his."

130def discover_assets(business_name, phone, location):
131    variants = _phone_variants(phone)
132
133    queries = [
134        f"{phone} מזגנים",
135        f"{phone} {business_name}",
136        f"{business_name} {location}",
137        f"{business_name} site:d.co.il"
          # + site:b144.co.il OR site:facebook.com
138    ]
139
140    candidate_urls = set()
141    with DDGS() as ddgs:
142        for query in queries:
143            try:
144                results = ddgs.text(query, max_results=6)
145                for r in results:
146                    url = r.get("href", "")
147                    domain = urlparse(url).netloc.replace("www.", "")
148                    if not any(
149                        skip in domain
150                        for skip in SKIP_DOMAINS
151                    ):
152                        candidate_urls.add(url)
153            except Exception as e:
154                print(f"  [Search error: {e}]")
155
156    verified = []
157    for url in candidate_urls:
158        text = scrape_url(url)
159        if text.startswith("[ERROR"):
160            continue
161        if any(v in text for v in variants):
162            verified.append(url)

Line by line
queries = [ f"{phone} מזגנים", f"{phone} {business_name}", ... ]
4 different search queries, not 1. Each query approaches the problem differently. Phone + category is most reliable for Israeli businesses. Phone + name handles directories. Name + location catches Google Maps entries. The site: query targets specific directories.
candidate_urls = set()
Set prevents duplicates automatically. If the same URL appears in results from two different queries, set.add() silently ignores the second occurrence. A list would add it twice.
with DDGS() as ddgs: results = ddgs.text(query, max_results=6)
DuckDuckGo search. DDGS() opens a session. ddgs.text() runs a web search and returns a list of dicts, each with "href" (URL), "title", and "body" (snippet). max_results=6 limits results per query — 4 queries × 6 results = max 24 candidates.
if not any(skip in domain for skip in SKIP_DOMAINS):
Filter out social media and useless sites. any() returns True if at least one item matches. "not any(...)" = none of the skip domains appear in this domain. Filters google.com, facebook.com, instagram.com etc. before even trying to scrape.
if any(v in text for v in variants): verified.append(url)
The core verification logic. Scrapes the candidate URL, then checks if any phone format appears in the page text. If the phone number is on the page, this is genuinely the client's site. If not — even if the name matches — it gets rejected. This is how we distinguish "יגאל מזגנים" in Krayot from "יגאל מזגנים" somewhere else.
if text.startswith("[ERROR"): continue
Skip unreachable URLs. scrape_url() returns an error string for failed requests. "continue" skips to the next iteration of the for loop. We don't add unreachable URLs to verified.

llm.py

All Claude API calls. Every function builds a system prompt + user prompt and calls call_claude().

💡 What is an SDK — and what is "client"?

Before reading any Claude API code, understand these two concepts. They appear in the very first lines of llm.py and in every function.

SDK — Software Development Kit
A pre-written package that hides the hard parts. Without it you'd manually write HTTPS requests, format JSON bodies, parse responses, handle errors.
Without SDK (manual):
requests.post("https://api.anthropic.com/v1/messages", headers={...}, json={...})
With SDK:
client.messages.create(...)
client — the connection object
client is just a variable name — it holds the Anthropic SDK object. Created once at the top of llm.py, reused by every function.
from anthropic import Anthropic
client = Anthropic(api_key="sk-ant-...")

# now every function uses:
client.messages.create(...)
Why client.messages.create() — what does .messages mean?

The Anthropic SDK is organized into namespaces. client.messages is the "messages" section of the API — the one that handles conversations. Claude has other API endpoints too (like for embeddings), but we only use messages.

client
The Anthropic SDK object. Holds your API key.
.messages
The messages API namespace — for chat/conversation calls.
.create(...)
Creates a new message — sends the request, waits, returns Claude's response.
Interview answer: "I used the official Anthropic Python SDK. It handles authentication, request formatting, and response parsing. I create one client object at module level and reuse it across all API calls. To send a prompt I call client.messages.create() with a system prompt, a user prompt, and a max_tokens limit — and get the response text back."

Line by line
system = """..."""
Triple-quoted string — the system prompt. Everything between the triple quotes is the string, even across multiple lines. The key instruction here is "Return ONLY valid JSON" — without this Claude adds explanations that break json.loads().
prompt = f"""... {{ "business_name": "Hebrew business name", ... }} SCRAPED DATA: {scraped_text}"""
f-string with escaped braces and one real variable. {{ and }} are escaped braces — Claude receives literal { and }. {scraped_text} (single braces) is the real variable — Python injects the actual scraped text here. The JSON schema tells Claude exactly what fields to extract and what to name them.

Strips markdown code fences if Claude added them. split("\n", 1)[1] removes the first line (```json). rsplit("```", 1)[0] removes the closing ``` from the end. The 1 limits each split to once — protecting against content that might contain backticks.

Line by line
f"ZAP-{datetime.now().strftime('%Y%m%d%H%M%S')}"
Generates a unique ID from the current time. strftime formats a datetime object into a string. '%Y%m%d%H%M%S' → "20260425143022". Combined with "ZAP-" prefix: "ZAP-20260425143022". Running the pipeline twice in the same second would produce the same ID — a known limitation of this prototype.
datetime.now().isoformat()
ISO 8601 timestamp. Produces "2026-04-25T14:30:22.123456". This is the international standard format that all CRM systems, databases, and APIs understand. Using it makes the data portable.
"client_data": json.loads(client_card) if isinstance(client_card, str) else client_card,
Inline ternary — handles two possible types. client_card might arrive as a string (JSON text) or already as a dict. isinstance(client_card, str) checks its type. If it's a string, json.loads() parses it into a dict. If it's already a dict, use it directly. This makes the function flexible.
"welcome_message_preview": welcome_message[:500] + "..." if len(welcome_message) > 500 else welcome_message,
String slicing + conditional. welcome_message[:500] takes the first 500 characters. If the message is longer, append "...". If it's shorter, use the full message. This keeps the CRM entry compact — the full message is saved separately in welcome_message.md.
json.dump(crm_entry, f, ensure_ascii=False, indent=2)
Writes Python dict to disk as formatted JSON. ensure_ascii=False means Hebrew characters are saved as-is (not as \uXXXX escape sequences). indent=2 makes the JSON human-readable with 2-space indentation. Without indent, it would be one long unreadable line.
"actions_taken": [ {...}, {...}, {...}, {...}, {...} ]
Audit trail — 5 actions recorded. In a real CRM each action would be logged separately as it happens. Here we log them all at the end with the same timestamp, which is a simplification. But the structure is identical to what a real CRM entry would look like.
